# Deterministic personalization — Phase 3

## Saved profile versus today's intent
GET/PUT /me/preferences stores dietary_pattern, allergies, liked/disliked canonical IDs, qualitative goals, default_servings (1–12), optional default_max_minutes (5–240). Allergies are a distinct typed safety field/JSON column, not dietary tags or soft goals. Empty allergy data means no recorded exclusions, never a safety guarantee.

POST /me/recipes/recommend accepts **MealIntent**, not a complete profile: optional craving (defaults to generic yemek), servings, max_minutes, an additional dietary_pattern, temporary_tags, today's optional budget, allow_disliked, and temporary pantry_adjustments. Explicit servings/time override defaults; missing time uses saved preference or 30 minutes. Intent and overrides are never saved to the profile or pantry and have no DB table. Budget is validated but unapplied. The anonymous Phase 1 request/response contract remains unchanged.

## Actual hierarchy and algorithm
1. Reject known allergen ingredients. If any selected allergy exists, also exclude any recipe containing an ingredient whose allergen_metadata_complete is false. Optional ingredients count too; they cannot silently bypass an allergy.
2. Apply both saved and today's dietary hard restrictions (intersection; today's standard cannot loosen saved vegetarian). All non-standard saved/current diets also conservatively exclude incomplete compound-ingredient metadata. Vegetarian excludes meat, vegan excludes animal ingredients, pescatarian excludes meat except fish-category ingredients. Gluten-free excludes known gluten or incomplete ingredient metadata. The lactose_free code conservatively excludes milk-containing or incomplete ingredients; it does not measure lactose or certify a clinical restriction. UI says süt içeren malzemeler hariç.
3. Detect a recognized query ingredient absent from the constrained candidate pool. Return recipes=[] with an actionable conflict message; e.g. saved vegetarian + tavuk never returns chicken. Allergy exclusions cannot be overridden by the intent.
4. Apply today's explicit total-time limit, otherwise the default, and the existing deterministic query matching rules.
5. Exclude any disliked ingredient, including optional ones. allow_disliked=true is a temporary, explicit escape hatch only for dislikes; it never changes allergies, diet or time.
6. Rank eligible candidates lexicographically by number of saved/temporarily declared pantry matches (positive known quantity or unknown presence), then liked ingredient matches, then goal matches, then the original Phase 1 score, then ascending total duration and slug. This preserves the required priority instead of letting a large soft score overcome hard constraints. Rank all matching candidates before choosing up to five; the anonymous endpoint still keeps its original limit behavior.

Existing Phase 1 score includes its small pantry bonus, but the higher-priority pantry count above is authoritative. Pantry is a usefulness signal, not confirmation that the quantity is sufficient. Saved quantities are only allocated by the basket service. Today’s pantry adjustments replace one ingredient's saved entry for this request only; repeated adjustment IDs are rejected. An explicit zero quantity can represent no usable stock temporarily.

Goal signals: high_protein matches the internally authored protein kaynağı tag; quick means total <=30 minutes; economical matches ekonomik; student_friendly means economical and <=30; light matches hafif. Saved and today's goals are unioned/deduplicated. balanced is stored but adds no additional score until a deterministic definition is established. These are qualitative labels, not verified nutrients, price estimates, clinical nutrition, ML or AI.

Responses preserve recipe/scaling/provenance fields and add profile_applied, applied_servings, applied_max_minutes, conflicts and per-match pantry/liked/goal signal counts. Reasons explain the known matches. A conflicting liked ingredient is allowed in a saved profile but never bypasses an allergy; its unsafe recipe is simply excluded.

## Allergen metadata and honest boundaries
Supported safety concepts: milk, egg, gluten, peanut, tree_nut, shellfish, fish, soy. The 37-ingredient internal review annotates intrinsic allergens of plain ingredients (e.g. milk products, eggs and gluten grains). Generic pasta, bread, cream and tomato paste have incomplete compound-ingredient metadata; they are conservatively excluded whenever allergies are selected. Future registry entries default to incomplete, not presumed safe. Schema checks reject reviewed dairy/egg/gluten ingredients missing the corresponding known allergen. Complete here means an internal plain-ingredient review, not laboratory testing, supplier certification or product-label verification.

All personalized results and the allergy UI explicitly tell users to check product labels and explain that Tencerem does not replace professional medical advice or guarantee allergen/cross-contact safety. There are no actual retailer product ingredient lists. Anonymous results remain a trial, without account-specific allergy exclusions; the UI makes account/anonymous scope visible. A saved-pantry basket additionally rejects selections incompatible with the saved diet/allergy constraints. Explicit anonymous basket requests remain profile-independent.

## Verified cases and limitations
Tests cover vegetarian + chicken conflict; milk allergy beats liked cheese; incomplete metadata fails closed under a selected allergy; hard time beats likes; dislikes exclusion and temporary override; liked-ingredient ordering; qualitative goal signals; default-vs-explicit time/servings; and persistence/user isolation. No stemming, fuzzy matching, negation understanding or arbitrary food substitution is introduced. Expiration dates do not affect filtering, safety assessment or ranking in Phase 3. Future personalization changes need explicit tests of hard constraints before adjusting soft ranking.
